1. Estructura de una aplicación web

El problema típico es el "¡en mi máquina sí funcionaba!": la app no arranca en el servidor porque no se ha definido bien el entorno. Una app web no es un .exe, es un conjunto de componentes que trabajan juntos.

Las 4 partes de una app web

ParteQué esEjemplo
Código fuenteFrontend: lo que el usuario ve (HTML, CSS, JS).
Backend: el motor oculto (Java, PHP, Python, Node.js) que valida logins, procesa pagos, usa la BD.		El HTML de la lista de tareas / el código que guarda las tareas en la BD.
Archivos estáticosNo cambian con la lógica y suelen pesar: imágenes, vídeos, PDF, fuentes, CSS base.El logo de Netflix.

Dependencias / libreríasCódigo de terceros para no "reinventar la rueda". Backend: npm, pip, Maven, Composer. Frontend: jQuery, Moment.js.El driver de MySQL para Java.

Los 5 requerimientos de implantación

  1. Entorno de ejecución (runtime): el software base. Java → JRE/JDK; Node.js → intérprete de Node. "Es el corazón del sistema".
  2. Servidor web y/o de aplicaciones: cuál y en qué puertos (Apache para estáticos, Tomcat para Java; 80, 8080).
  3. Base de datos: motor exacto (MySQL 8.0, MongoDB), IP de conexión, usuario y contraseña propios de la app.
  4. Gestor de dependencias: npm (Node), Composer (PHP), Maven (Java) instalados en el servidor.
  5. Variables de entorno: ¡crítico! Claves API y modo desarrollo/producción. Cambian según el entorno y no deben ir en el código (seguridad).
Truco para el testSi preguntan dónde van las claves API o contraseñas: en variables de entorno, nunca escritas en el código fuente.

2. Documentar los procesos

La documentación es la memoria colectiva del equipo: sirve cuando termina un proyecto, cuando un compañero coge el relevo o cuando hay que repetir un despliegue meses después.

¿Por qué documentar? (3 motivos)

  1. Equipo y colaboración: transferir conocimiento, que cualquiera entienda el despliegue.
  2. Mantenimiento y resolución de problemas: diagnosticar rápido y mantener el servicio.
  3. Escalabilidad y futuras mejoras: replicar entornos, migrar, montar servidores nuevos.

Elementos de una buena documentación (5)

Tiene que ser clara, precisa y completa:

  • Prerrequisitos de hardware y red: RAM, CPU, disco y puertos a abrir en el firewall (ej. 8088).
  • Comandos exactos literales, paso a paso (ej. sudo apt install docker.io).
  • Rutas y cambios de configuración: dónde está el archivo (ej. server.xml) y el "antes" y "después".
  • Capturas de hitos: ej. la consola con "active (running)".
  • Troubleshooting: errores comunes y su solución.

3. Arquitecturas web y modelos

Las 3 capas

  • Capa cliente: el navegador del usuario, la interfaz.
  • Capa de negocio: la lógica y las reglas de negocio a las que accede el cliente.
  • Capa de datos: almacenamiento (gestores de BD relacionales, ficheros XML o texto plano).

Monolítico: "todo en uno"

Todo (interfaz, lógica, datos) empaquetado y desplegado como una única unidad. "Una casa de una sola habitación". Si hay que escalar o actualizar algo, se hace con toda la app.

Cliente-Servidor

Dos partes: el cliente (navegador o app móvil) pide y el servidor (lógica + datos) responde. "Un restaurante: tú pides, la cocina prepara".

Microservicios

Muchas apps pequeñas e independientes, cada una con su lógica y su propia BD. El usuario entra por un API Gateway que reparte las peticiones. "Una orquesta, cada músico con su partitura".

4. Protocolos: HTTP y HTTPS

HTTP (HyperText Transfer Protocol) es el "idioma" de la web: las reglas de cómo se formatean y envían los mensajes entre cliente y servidor. Escribes una URL → el navegador manda una petición GET → el servidor busca el recurso y lo devuelve en una respuesta.

ClaveHTTP es sin estado (stateless): cada petición es independiente y el servidor "olvida" las anteriores ("taquillero de cine con mala memoria"). Para que Instagram "te recuerde" se usan cookies y sesiones (la cabecera Set-Cookie de la respuesta).

Petición HTTP

  • Método: GET (pedir), POST (enviar, ej. formulario), PUT/PATCH (actualizar), DELETE (borrar)
  • URL: dirección del recurso
  • Versión: HTTP/1.1, HTTP/2
  • Cabeceras: User-Agent, Accept-Language, Authorization
  • Cuerpo (opcional): datos, se usa con POST/PUT

Respuesta HTTP

  • Código de estado (3 cifras)
  • Mensaje de estado (ej. "OK")
  • Cabeceras: Content-Type, Content-Length, Set-Cookie
  • Cuerpo: HTML, JSON, imagen...
FamiliaSignificaEjemplos que tienes que saber
2xxÉxito200 OK
3xxRedirección301 Moved Permanently
4xxError del cliente404 Not Found, 403 Forbidden (sin permiso; el que te salió en los ejemplos de Tomcat)
5xxError del servidor500 Internal Server Error

HTTPS

En HTTP todo va en texto plano: en una wifi pública (ej. aeropuerto) un programa "sniffer" puede leerlo. HTTPS no es un protocolo nuevo: es HTTP sobre una capa de seguridad TLS/SSL. Al conectar, cliente y servidor hacen un handshake TLS: negocian el cifrado y verifican al servidor con un certificado digital. Ejemplo de la postal: HTTPS es meter la postal en una caja fuerte.

  • Confidencialidad: el cifrado impide leer los datos interceptados.
  • Integridad: los datos no se han modificado por el camino.
  • Autenticidad: el certificado confirma que el servidor es quien dice ser (evita suplantaciones).

Se ve con el candado y https://. Si una web te pide la tarjeta o el DNI sin HTTPS: no metas los datos y sal. Puertos por defecto: HTTP 80, HTTPS 443.

5. Servidor web vs servidor de aplicaciones

Servidor webServidor de aplicaciones
SirveContenido estático (HTML, CSS, JS del cliente, imágenes, PDF). No cambia salvo que lo edites a mano.Contenido dinámico: ejecuta código, consulta la BD y genera una respuesta para cada usuario.
Puntos fuertesMuy rápido, usa caché, muchos usuarios a la vez. Bajos requerimientos: no necesita runtime de un lenguaje."El cerebro de la lógica de negocio": logins, saldo del banco, formularios.
EjemplosApache HTTP Server, NginxTomcat (Java: servlets, JSP) · Node.js (Express, NestJS) · Gunicorn/uWSGI (Python: Django, Flask) · PHP-FPM (WordPress, Laravel)
Puerto típico80 (443 con HTTPS)Tomcat: 8080

A menudo el servidor web hace de proxy: recibe la petición y, si es dinámica, se la pasa al servidor de aplicaciones.

Pregunta de reflexión del tema¿Solo servidor de aplicaciones para todo (también imágenes y CSS)? Funcionaría, pero gastaría recursos del runtime en archivos que no necesitan lógica y sería más lento.
¿Solo servidor web para una app dinámica como un foro? No funcionaría: no puede ejecutar la lógica (login, guardar mensajes, BD). Por eso se combinan los dos.

6. Virtualización: VMs, nube y contenedores

Todo esto busca resolver el "funciona en mi máquina, pero no en la tuya".

Máquinas virtuales

Un ordenador completo dentro de otro: su propio SO, RAM, disco y CPU virtuales. Se gestionan con VirtualBox o VMware, y quien las gestiona es el hipervisor. Las empresas meten cientos de servidores virtuales en pocas máquinas físicas.

Ventajas VMDesventajas VM
Aislamiento total (si una falla no afecta a las demás)
Independencia del SO (Linux dentro de Windows)
Portabilidad entre hosts
Recursos garantizados (RAM/CPU asignada)		 Alto consumo (un SO completo por VM)
Arranque lento (como encender un PC)
Grandes y pesadas (varios GB)
Sobrecarga del hipervisor

La nube

Normalmente son VMs en centros de datos de Amazon (AWS), Google (GCP) o Microsoft (Azure). Se alquilan por horas o minutos, se escalan o apagan según la necesidad, sin comprar hardware. Además hay almacenamiento, BD gestionadas, redes... Netflix o Spotify la usan para picos (Black Friday, estrenos) y pagan solo lo que usan.

Contenedores

Si una VM es un apartamento completo, un contenedor es una caja estandarizada y ligera: solo el código, librerías, dependencias y configuración. No llevan un SO completo: comparten el kernel del SO del host.

Ventajas contenedoresDesventajas contenedores
Extremadamente ligeros (arrancan en segundos)
Portabilidad total
Consistencia del entorno (adiós al "en mi máquina funciona")
Escalabilidad rápida (cientos en una máquina)
Desarrollo ágil (CI/CD)		 Menor aislamiento que las VMs (comparten kernel)
Dependencia del SO del host (un contenedor Linux no va directo en Windows sin una VM ligera, por eso Docker Desktop usa WSL2)
Curva de aprendizaje

Docker

La plataforma más popular, el estándar de facto (no la única).

  • Dockerfile: archivo de texto con las instrucciones para construir una imagen.
  • Imagen: plantilla inmutable con todo lo necesario para ejecutar la app.
  • Contenedor: una instancia ejecutable de una imagen. De una imagen salen muchos contenedores.
Pregunta del tema¿Qué ventaja tiene que me pasen una imagen Docker en vez del código? La imagen ya trae el runtime, las dependencias y la configuración, así que funciona igual en mi equipo sin instalar nada más que Docker. Con el código fuente tendría que montar yo todo el entorno.

7. Código y comandos que te pueden pedir a mano

Sale de los talleres (Apache, Tomcat y Docker en Linux y Windows). No hace falta memorizar todo: con saber qué comando hace qué y qué archivo se toca para el puerto, vas bien.

Apache en Linux (Ubuntu)

# instalar y ver estado
sudo apt update
sudo apt install apache2
sudo systemctl status apache2
sudo systemctl restart apache2      # start / stop / restart / enable

# puerto  ->  /etc/apache2/ports.conf
Listen 8088

# sitio   ->  /etc/apache2/sites-available/000-default.conf
<VirtualHost *:8088>
    DocumentRoot /var/www/personal
</VirtualHost>

sudo apache2ctl configtest          # comprueba la sintaxis -> Syntax OK
sudo ufw allow 8088/tcp             # abrir el puerto en el cortafuegos
curl http://localhost:8088          # probar

Carpeta web por defecto: /var/www/html. Usuario de Apache: www-data.

Apache en Windows

# archivo: C:\Apache24\conf\httpd.conf
Define SRVROOT "C:/Apache24"
Listen 80
DocumentRoot "${SRVROOT}/htdocs"

httpd.exe -k install      # instalar como servicio (cmd como administrador)
httpd.exe -k start
httpd.exe -t              # comprobar la configuración

Necesita el Visual C++ Redistributable (VC_redist) instalado.

Tomcat (Linux y Windows)

# necesita Java (JDK) -> variable JAVA_HOME
# Linux: bin/setenv.sh
export JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64
# Windows: Variables de entorno del sistema -> JAVA_HOME = C:\Program Files\Java\jdk-21

# puerto -> conf/server.xml  (por defecto 8080)
<Connector port="9090" protocol="HTTP/1.1"
           connectionTimeout="20000"
           redirectPort="8443" />

# arrancar / parar
./bin/startup.sh     ./bin/shutdown.sh      # Linux
bin\startup.bat      bin\shutdown.bat       # Windows

# log de arranque
logs/catalina.out   ->  "Server startup in ... milliseconds"

Usuarios del Manager: conf/tomcat-users.xml. Las apps se despliegan en webapps/ (un .war se descomprime solo).

Docker

# instalar en Ubuntu y usarlo sin sudo
sudo apt install docker.io
sudo usermod -aG docker $USER       # luego cerrar sesión
docker run hello-world              # "Hello from Docker!"

# comandos básicos
docker pull nginx                   # descargar imagen
docker images                       # ver imágenes
docker ps        /  docker ps -a    # contenedores en marcha / todos
docker stop web  /  docker rm web   # parar / borrar contenedor
docker rmi nginx                    # borrar imagen

# web estática SIN Dockerfile (montando la carpeta)
docker run -d -p 8080:80 --name web -v "$(pwd)":/usr/share/nginx/html nginx
#  -d = segundo plano · -p HOST:CONTENEDOR · --name nombre · -v carpeta:ruta
# Dockerfile para una web estática
FROM nginx:alpine
COPY ./web /usr/share/nginx/html
EXPOSE 80

# construir la imagen y lanzar el contenedor
docker build -t miweb .
docker run -d -p 8080:80 --name web miweb
# abrir http://localhost:8080

Con Apache en vez de Nginx: FROM httpd:2.4 y COPY ./web /usr/local/apache2/htdocs/.

9. Preguntas cortas (con respuesta)

Intenta contestarla en voz alta y luego abre la respuesta.

¿Qué es una arquitectura monolítica? Di una ventaja y un inconveniente.

Toda la aplicación (interfaz, lógica y datos) se empaqueta y despliega como una única unidad. Ventaja: es sencilla de desarrollar y desplegar al principio. Inconveniente: para escalar una parte hay que escalar toda la aplicación, y un cambio en una parte puede afectar a todo (acoplamiento alto).

Diferencia entre servidor web y servidor de aplicaciones, con un ejemplo de cada.

El servidor web sirve contenido estático (HTML, CSS, imágenes) de forma rápida, por ejemplo Apache HTTP Server o Nginx. El servidor de aplicaciones ejecuta código para generar contenido dinámico y trabaja con la base de datos, por ejemplo Apache Tomcat para Java.

¿Qué significa que HTTP es "sin estado"? ¿Cómo se mantiene una sesión?

Cada petición es independiente y el servidor no recuerda las anteriores. Para mantener la sesión se usan cookies: el servidor envía una cookie de sesión con la cabecera Set-Cookie y el navegador la manda en cada petición siguiente.

Partes de una petición HTTP y de una respuesta HTTP.

Petición: método (GET, POST...), URL, versión del protocolo, cabeceras y cuerpo opcional. Respuesta: código de estado, mensaje de estado, cabeceras y cuerpo.

¿Qué es HTTPS y qué tres cosas garantiza?

Es HTTP funcionando sobre una capa de seguridad TLS/SSL. Al conectar se hace un handshake y el servidor se identifica con un certificado digital. Garantiza confidencialidad (nadie lee los datos), integridad (no se modifican) y autenticidad (el servidor es quien dice ser).

Diferencia entre una máquina virtual y un contenedor.

La VM incluye un sistema operativo completo y la gestiona un hipervisor: está totalmente aislada pero consume muchos recursos y arranca lento. El contenedor solo lleva la aplicación y sus dependencias y comparte el kernel del sistema anfitrión: es mucho más ligero y arranca en segundos, pero aísla algo menos.

Define Dockerfile, imagen y contenedor.

Dockerfile: archivo de texto con las instrucciones para construir una imagen. Imagen: plantilla inmutable con todo lo necesario para ejecutar la aplicación. Contenedor: instancia en ejecución de una imagen.

Nombra los 5 requerimientos de implantación de una aplicación web.

Entorno de ejecución (runtime), servidor web y/o de aplicaciones con sus puertos, base de datos, gestor de dependencias y variables de entorno.

¿Por qué las claves API y contraseñas van en variables de entorno?

Porque así no quedan escritas en el código (que se comparte y se sube a repositorios) y se pueden cambiar según el entorno (desarrollo o producción) sin tocar el código. Es una cuestión de seguridad.

¿Qué debe incluir la documentación de una instalación?

Prerrequisitos de hardware y red (RAM, CPU, puertos), los comandos exactos, las rutas de los archivos de configuración con el antes y el después, capturas de los pasos importantes y una sección de troubleshooting con errores comunes y su solución.

¿Qué es un API Gateway y en qué modelo se usa?

Es la puerta de entrada de la arquitectura de microservicios: recibe las peticiones del usuario y las reparte al microservicio que corresponda.

¿Por qué un contenedor Linux no funciona directamente en Windows?

Porque los contenedores comparten el kernel del sistema anfitrión y el contenedor necesita un kernel Linux. En Windows hace falta una VM ligera por medio (WSL2 en Docker Desktop).

¿Qué haces si una web te pide la tarjeta de crédito y no tiene HTTPS?

No meter los datos y salir de la web, porque viajarían en texto plano y cualquiera que intercepte el tráfico podría leerlos.

Explica qué hacen estos comandos: docker run -d -p 8080:80 --name web nginx

Crea y arranca un contenedor a partir de la imagen nginx, en segundo plano (-d), llamado "web" (--name), y conecta el puerto 8080 del equipo con el puerto 80 del contenedor (-p). Se accede con http://localhost:8080.

¿En qué archivo cambias el puerto de Apache (Ubuntu) y el de Tomcat?

Apache: /etc/apache2/ports.conf (directiva Listen) y el VirtualHost del sitio. En Windows, en httpd.conf. Tomcat: en conf/server.xml, atributo port del Connector HTTP/1.1 (por defecto 8080).
